# Decisions

One or two lines each: date, decision, reason. Planning documents live in `F:\Work\DOCS`.

- 2026-11-24 — npm instead of pnpm. It ships with Node, so there is one less tool to install; the plan does not depend on pnpm.
- 2026-11-24 — Next.js 16.4 (App Router, Turbopack, Cache Components on), TypeScript, Tailwind 4, shadcn/ui. As created by `create-next-app@latest`; this version differs from older Next.js, so its bundled docs in `node_modules/next/dist/docs/` are the reference.
- 2026-11-24 — Two Supabase projects, `tryon-dev` (local + Vercel previews) and `tryon-prod` (production only). Real user data never touches dev.
- 2026-11-24 — The database is changed only through migration files in `supabase/migrations/`, applied with the Supabase CLI. No edits in the dashboard table editor.
- 2026-11-25 — The browser only reads its own rows and edits harmless columns (profile details, primary photo, try-on rating). Photo status, try-on jobs, consents and private files are written by the server with the secret key, so moderation, limits and costs cannot be bypassed from the browser. Tighter than "users read and write their own rows" in the implementation guide.
- 2026-11-25 — Database rules that back up the app code: max 5 non-rejected photos per user; one done result and one in-flight job per (photo, product, provider), which is the cache and stops double charges; a try-on must use the same user's photo; a product cannot be published without a try-on image and a buy link.
- 2026-11-25 — Added `products.slug` (unique) for readable URLs and a seed script that is safe to run twice. `cost_cents` is numeric so $0.075 is stored exactly as 7.50.
- 2026-11-25 — The profile-creation trigger (planned for step 1.3) is in the first migration, since every other table depends on users having a profile.
- 2026-11-25 — One Supabase project for now: `tryon-prod` is used for local work, previews and production (owner's choice, replacing the dev/prod split above). Fine while there are no real users. Before real users arrive (Stage 2), either bring `tryon-dev` back for local work and tests, or never run `test:rls` and seed scripts against data that real people use.
- 2026-11-25 — Supabase CLI 3.x targets the local stack by default, so `db:push` and `db:types` pass `--remote` (the linked project).
- 2026-11-25 — No Docker on the dev machine, so no local Supabase. The migration is checked on an in-memory Postgres before pushing, and `npm run test:rls` checks the real dev project.
- 2026-11-25 — Sign-in uses Supabase Auth through `@supabase/ssr` (session in cookies). `proxy.ts` (Next 16's name for middleware) refreshes the session and does a fast redirect; the real check is `requireUser()` on the server in every protected page and action.
- 2026-11-25 — Consents are written by the server with the secret key, with the IP address. Google users have not ticked the boxes, so any signed-in user without `is_adult_confirmed_at` is sent to `/welcome` first.
- 2026-11-25 — Email links use `token_hash` templates so they work on any device; the callback also accepts `?code=` (Google, default templates).
- 2026-11-25 — Minimum password length 8. Sign-up and reset never reveal whether an email has an account.
- 2026-11-25 — Terms and privacy pages are short drafts with a version string stored with each consent. A lawyer writes the real ones before Stage 5.
- 2026-11-25 — Measurements are stored in metric (0.1 precision) and shown in the user's units: height in whole cm or ft/in, weight in 0.1 kg or whole lb, chest/waist/hips in whole cm or half inches. Imperial is the default (US market). Conversions live in `lib/units.ts` with unit tests (`npm test`, vitest).
- 2026-11-25 — `@types/node` raised to 24 to match the Node version in use (vitest needs it).
- 2026-11-25 — Photo moderation uses OpenAI `omni-moderation-latest` (free) instead of Google Vision SafeSearch ($1.50 per 1,000 after 1,000 free). Thresholds in `lib/moderation/policy.ts`: "sexual" blocks only at 0.85 so swimwear/underwear passes; anything suggesting minors blocks at 0.1. To be tuned with realistic photos before Stage 2. Fails closed in production when the service or key is missing.
- 2026-11-25 — Uploads go through a route handler (`POST /api/photos`) rather than a Server Action, to accept files up to 4 MB. The server re-encodes every photo with sharp, so metadata is removed even if the browser step is bypassed. Rejected photos store no file, only a row with the category, for abuse review.
- 2026-11-25 — The consent text names the services that receive photos (`PHOTO_PROCESSORS` in `lib/legal.ts`: OpenAI, FASHN AI). If Stage 0 picks a different try-on provider, change the list and `BODY_PHOTO_VERSION` so everyone is asked again.
- 2026-11-25 — For step 1.11 (account deletion): deleting an auth user does not remove their storage files, and their session token stays valid until it expires (about an hour), because sessions are checked locally. Deletion must remove files first and sign the user out.
- 2026-11-25 — No scraping of Amazon or other shops: their terms forbid it, the photos are copyrighted, and try-on changes the images. The catalog uses drawn placeholder products until brands give written permission; a Shopify importer is planned for the first brand that says yes.
- 2026-11-25 — Size charts are JSON on the product: body measurements in cm as inclusive ranges per size (format in the README). Postgres does not keep JSON key order, so size order comes from `products.sizes`.
- 2026-11-25 — Catalog reads use a cookie-less client and `'use cache'` (tag `products`, a few minutes), since the data is public. Product images go through `next/image`, allowed only for the public `product-images` bucket.
- 2026-11-25 — Starting a try-on is one database function (`start_tryon_job`, server only) that holds a lock while it checks the cache, a running job, the per-user limit and the site-wide cap, then creates the job. Two requests at once can't both pass a limit or both pay. Limits count new try-ons in a rolling 24 hours; failed jobs (free at FASHN) and cached results don't count.
- 2026-11-25 — The provider name stored on a job includes the model (`fashn-v1.6`, `fashn-max`, `mock`), so switching model never serves a cached result from another model. Default FASHN model is `tryon-v1.6` (stable); `tryon-max` is "Preview". Stage 0 decides.
- 2026-11-25 — The person photo goes to FASHN as a 10-minute signed link (FASHN fetches it once); the garment image is already public. Results are copied into our private bucket with the label; FASHN's own copy is deleted after 3 days.
- 2026-11-25 — Results are run through the same free moderation check as uploads. If that service is down the result is kept and the outage logged, since the input photo was checked and the provider filters its own output; a paid result is not thrown away.
- 2026-11-25 — The "AI-generated preview" label is a pre-rendered image (`scripts/make-ai-mark.mjs`), because Vercel's servers have no fonts for drawing text. The words are also written into the image's EXIF description.
- 2026-11-25 — One automatic retry, only for errors FASHN calls temporary (busy, pipeline, third-party, rate limit). The retry is claimed in the database first, so two polls at once can't both pay for it.
- 2026-11-25 — The stuck-job sweep runs daily, not every 5 minutes: Vercel's free Hobby plan allows cron jobs once a day. Polling and new requests also end jobs stuck over 3 minutes, so nothing waits on the cron. Back to every 5 minutes on a paid plan.
- 2026-11-25 — On the live site try-on is off until `TRYON_PROVIDER` is set, so the free mock (which returns the user's own photo) can never be shown to real users by accident.
- 2026-11-25 — The try-on start page (`/try/<product>`) shows the photo consent and upload in place, so a first-time user never leaves the flow. Waiting, result and failure are one page (`/tryons/<id>`) that updates itself, so leaving and coming back just works.
- 2026-11-25 — In the before/after slider the generated image is on the left and the user's photo on the right, so the "AI-generated preview" mark (bottom-left of the result) is always visible on the generated part. The slider uses pointer events on the whole image (iPhone Safari won't drag an invisible range input), with a hidden range input for the keyboard.
- 2026-11-25 — On phones the header's Account link is an icon, so the header fits on one line at 375 px.
- 2026-11-25 — Size suggestion: each measurement picks its size (the larger one when ranges overlap or it falls between sizes), and the suggestion is the largest of those, with a note where it may be loose. Above the chart there is no suggestion rather than a wrong one. It returns `{ size, reason, missing }` (a little more than the guide's `{ size, reason }`), so the page can ask for the missing measurements.
- 2026-11-25 — Inches in the size chart and in the reason are both rounded to the nearest half inch, so the two never disagree.
- 2026-11-26 — Buy clicks are recorded in our own table (`buy_clicks`) as well as PostHog, because they are what shops will be shown and billed on later; the database is the record. Deleting an account keeps its clicks without the user id.
- 2026-11-26 — Analytics events are sent from the server (PostHog capture API, no SDK): no cookies, no browser script, nothing to block, and each event fires once at the point where the thing really happened (e.g. `tryon_done` by the request that closes the job). Page-view analytics in the browser wait for the cookie notice (step 1.13). The privacy policy (step 1.13) must list PostHog.
- 2026-11-26 — Shop links get `utm_source=virtual-tryon&utm_medium=referral&utm_campaign=tryon`, unless the shop's link already sets them. A per-click id for shops to report sales back comes with affiliate deals.
- 2026-11-26 — Account deletion is immediate and complete (files, then the auth user with all rows by cascade, then files again, then a check that finds nothing). Consent records go too; if a lawyer says they must be kept as evidence, keep them without the link to the person. Buy clicks stay as anonymous counts.
- 2026-11-26 — Not yet covered by deletion: (1) PostHog keeps events under the user's id; before Stage 2, add a call to PostHog's person-deletion API (needs a personal API key) or stop sending the user id. (2) FASHN deletes its copies itself within 3 days; the confirmation page says so. (3) A session on another device stays usable for up to an hour (sessions are checked locally), but every write fails because the user no longer exists.
- 2026-11-26 — Data export goes through a private `exports` bucket and a 10-minute signed link, because Vercel limits a function's response to about 4.5 MB. ZIPs are made with `fflate` (no dependencies; 0.8.3, which fixes a reported issue in unzipping that we don't use anyway).
- 2026-11-26 — `getUser()` calls `connection()` first. With cache components and partial prefetching, Next.js pre-renders signed-in pages during prefetches, and Supabase's session check reads the current time, which Next.js reported as an error on `/account`, `/tryons` and `/photos`. Signed-in content now always renders per request.
- 2026-11-24 — Sentry and PostHog are wired once their accounts exist, still within step 1.1; the app runs without them.
